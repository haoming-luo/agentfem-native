# Scrum 轻量验证与对照方案

**状态：** 已采用  
**适用阶段：** 快速迭代、Gate 2/3 与 AgentFEM–Native 接入开发  
**原则：** 小闭环、高信息密度、按风险扩张，不把验证本身做成大工程

## 一、四层验证环

### L0：增量环

目标是在编码过程中几秒到十几秒内完成，只运行本次改动直接影响的测试。

最低要求：

- 一个最小正常场景；
- 一个关键恒等式、解析结果或不变量；
- 一个最可能出错的失败场景；
- 优化代码增加一次与可读基准层的完整输出对照；
- 修复缺陷时先加入能稳定复现它的最小回归测试。

L0 不运行跨平台矩阵、大网格、长时间积分、全量性能扫描或 FEniCSx 对照。

### L1：本地提交前环

当前完整 Python 测试只需不到一秒，因此提交可审查能力前运行：

```text
.venv/bin/python -m unittest discover -q
.venv/bin/python tools/check_independence.py
.venv/bin/python -m ruff check .
.venv/bin/python -m ruff format --check src tests benchmarks tools
```

科学代码还要运行与改动对应的 C++ 契约或小型差分测试。随着测试增长，L1 的
目标上限为一分钟；超过上限的案例迁入 L2，而不是删除科学断言。

### L2：里程碑本地环

只在一个可命名能力完成、准备推送 Gate 候选或修改 ABI 时运行：

- 完整 Python、C/C++ 契约与 sanitizer；
- 相关解析/制造解和网格或时间收敛；
- 三到五个固定代表规模的内存与性能记录；
- 本地 wheel 安装与 AgentFEM 最小集成；
- 需要时运行可选提供者或独立黑盒对照。

L2 不要求遍历所有参数组合。选择能覆盖不同失效机制的代表点，不选择大量相似
算例。

### L3：Tier-1 验收环

只在 Gate、平台、ABI 或阶段版本候选运行一次完整 GitHub Actions 验收：原生
Windows、Linux、macOS x86_64/arm64、Stable ABI、C++ 契约和必要的工件清单。
普通提交继续只跑 Linux 快检，纯文档提交不运行 CI。

## 二、按改动类型选择最小验证配方

| 改动类型 | L0 必须验证 | L2 才增加 |
|---|---|---|
| 网格/拓扑/DOF | 计数、连通性、方向或编号不变量、非法索引 | 畸变网格、重编号、较大图 |
| 基函数/积分/单元 | 分片统一性、精确积分阶次、对称性、刚体/常应变 | patch、制造解、收敛 |
| 装配优化 | 完整矩阵与载荷对照、无越界、无隐藏稠密化 | sanitizer、线程数不变量、规模性能 |
| 稀疏/求解器 | 已知小系统、残差、收敛与 breakdown | 条件数梯度、百万 DOF、提供者对照 |
| 材料模型 | 能量/应力关系、单步路径、非法参数 | 切线方向导数、循环路径、回滚 |
| 动力学/状态 | SDOF 单步、约束、能量、一次重启 | 波传播、时间阶、长时稳定 |
| 契约/Agent 接口 | Schema 往返、稳定错误路径、摘要变化 | AgentFEM 端到端与版本兼容 |
| 结果/I/O | 字段形状、单位/关联、摘要、路径安全 | wheel 安装、跨平台读取 |
| 仅性能实现 | 与基准层等价、规模/内存上界 | 重复计时、硬件身份、回归阈值 |

## 三、对照的优先顺序

每次只使用能回答当前风险的最低一层对照：

1. **数学真值：** 代数恒等式、手算小矩阵、解析解、守恒和能量关系；
2. **自有可读基准层：** NumPy 单元、装配和程序实现；
3. **自有实现差分：** Python/向量化/C++ 在相同输入上比较全部输出；
4. **通用提供者对照：** 在完全相同矩阵、右端项、约束、精度和停止规则下比较；
5. **第三方 FEM 黑盒：** 仅用于里程碑、兼容或独立交叉验证，且前四层至少已有
   一项非第三方依据。

FEniCSx 对照在隔离的验证环境中执行，只交换公开输入和数值结果，不把其源码、
内部对象或实现细节传入 Native。日常 L0/L1 不依赖 FEniCSx。

## 四、少而强的测试设计

- 优先使用 1–10 个单元的可手算网格，避免大型二进制 golden 文件；
- 同一场景通过参数化覆盖方向、重编号、材料区域和提供者，不复制测试代码；
- golden 数据只保存稳定的小矩阵、标量和摘要，不保存容易变化的大型文本输出；
- 随机测试使用固定种子和很小样本，失败后收缩成永久确定性回归案例；
- 每种能力只维护一个“金标准竖切案例”，其余测试验证独立风险；
- 不测试 Python/NumPy 本身，不为简单属性访问器堆低价值覆盖率；
- 覆盖率是发现遗漏的参考，不是成熟度或完成度指标。

## 五、容差纪律

- 精确结构身份（索引、图、命名集合、摘要）默认要求完全相同；
- 浮点量同时考虑绝对误差、相对误差和问题尺度；
- 位移、应力、残差、能量和反力使用各自有物理意义的判据；
- 并行归约若改变顺序，必须记录模式和差异，不能暗中放宽断言；
- 容差写在对应数学规格或集中登记处，不散落为无说明的魔法数字；
- 测试失败时先诊断缩放、条件数、归约顺序或模型差异，不直接加大容差。

## 六、性能验证保持轻量

日常增量只检查性能结构：没有隐藏稠密化、没有意外复制、临时内存有上界、热
循环没有回到 Python。因为工作站噪声，L0/L1 不设置严格墙钟门槛。

里程碑才记录三档规模：

- 小：验证固定开销和全部输出；
- 中：代表日常 AgentFEM 工程任务；
- 大：验证内存复杂度和目标规模。

只记录少量热身和重复样本、中位数及原始值。性能下降先作为诊断信号；只有在
固定硬件或稳定 CI 基线建立后，才设置自动回归阈值。

## 七、一个 Scrum 增量的完成定义

一个增量只有满足以下条件才算完成：

1. 有明确的 AgentFEM 未来消费场景和成熟度目标；
2. 数学规格只增加本次能力需要的最小内容；
3. 正常、恒等式/解析和失败三类最小证据通过；
4. 优化路径与可读基准层完整输出一致；
5. L0 和适用的 L1 检查通过；
6. 已知限制、未支持路径和成熟度没有被隐藏；
7. 只有 Gate 验收完成时才把 `implemented` 提升为 `verified`。

单次增量通常增加 3–8 个高价值测试，而不是追求几十个相似测试。若一个功能
需要大型验证框架才能开始，应先缩小功能边界。

## 八、轻量证据记录

日常提交只在测试名称、提交说明或简短记录中包含：

```text
场景 | 声明 | 真值/基准 | 最大差异 | 失败边界 | 成熟度
```

只有 L2/L3 里程碑才生成完整验证报告、性能 JSON 和平台运行链接。不得为同一
源提交重复生成内容等价的报告或跨平台运行。

## 九、当前项目的实际执行

- 当前 169 项 Python 测试可继续作为 L1 快速套件，不立即重构目录或引入新的
  测试框架；
- 新测试沿用标准库 `unittest`，除非现有方式确实无法表达所需性质；
- 下一阶段首先为 Gate 2 建立一张有限的 T3/T4 验收清单，不建设通用验证平台；
- AgentFEM–Native 接入只维护热、线性静力、线性动力三条端到端金标准；
- 全局非线性、MPI 和 GPU 在进入相应 Gate 前只保留隔离实验测试。
