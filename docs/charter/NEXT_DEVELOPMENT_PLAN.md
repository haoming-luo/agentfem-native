# AgentFEM Native 后续架构与开发计划

**规划日期：** 2026-09-13  
**规划状态：** 执行建议；不自动提升任何科学能力的成熟度  
**当前基线：** `0.7.0a1`、Gate 2 基础线性静力 `verified`、C++ ABI 1.5、
194 项本地测试；Gate 2 源提交 `654fe02` 已在运行 `35461748299` 中通过完整
Tier-1 验收，ABI 1.5 源提交 `28b2ce7` 已在运行 `35462761452` 中独立通过
三平台验收

当前最近一次时间盒执行见
[`FIVE_HOUR_PREPARED_MECHANICS_SPRINT.md`](FIVE_HOUR_PREPARED_MECHANICS_SPRINT.md)：
已把可复用图接入 T3/T4、提供者和 T3 动力学；ABI 1.5 进一步消除串行预备
装配的重复 COO 行列索引，并保留清晰性能边界。

**唯一首要使用者：** AgentFEM 的未来工程模型、Agent 工作流和可信计算系统。
Native 可以保留独立 Python/CLI 入口用于开发、验证和集成，但不发展成与
AgentFEM 平行的终端产品。

**战略定位：** 面向 AgentFEM 的国产替代、自主掌握有限元求解内核。是否
“自主”以能否独立解释、维护、优化、构建、验证和替换关键计算路径为准，而不以
是否完全拒绝第三方通用库为准。

## 一、核心判断

AgentFEM Native 已经越过“能不能独立做有限元”的证明阶段。下一阶段的主要
风险不再是功能太少，而是已实现的 T3、T4、稀疏求解、动力学、状态和 Agent
接口继续以平行功能增长，最终形成难以优化和验证的多条路径。

因此，后续开发只围绕一条生产主干推进：

```text
AgentFEM 工程意图
  -> 版本化求解请求
  -> 不可变 KernelPlan
  -> 网格/空间/单元/材料批次
  -> 装配或算子应用
  -> 稀疏求解提供者
  -> 程序与事务状态
  -> 结果、守恒量和证据清单
```

短期不建设通用弱形式语言，也不追求任意单元和任意物理场。AgentFEM 已经拥有
面向工程的上层语言；Native 更应成为高性能、可审计、可被 Agent 安全操作的
力学执行引擎。

所有需求进入路线图前必须具有一个 AgentFEM 消费场景，并明确：工程意图如何
降低、Native 拥有哪些数值语义、Agent 如何预检、结果如何返回、证据如何被
AgentFEM 保存与解释。单纯为了“像其他有限元库一样拥有”而增加的功能不进入
关键路径。

## 二、从成熟内核吸收什么

本规划只参考公开文档中的能力划分，没有查看、复制或改写任何第三方有限元
实现源码。

FEniCSx 的长期价值来自清晰的组件分工：UFL 表达离散变分形式，FFCx 负责
编译阶段，Basix 负责参考单元、基函数、积分和 DOF 变换，DOLFINx 运行时则
分离 mesh、graph、fem、linear algebra 和 I/O。其公开文档也显示，PETSc、MPI、
分区器和并行 I/O 会显著扩大安装与运行时依赖面。AgentFEM Native 应吸收这种
“分层和可替换边界”，但不复制其 DSL、对象模型或实现，也不让完整 HPC 栈成为
Windows/macOS/Linux 串行核心的前置条件。

Akantu 的优势是力学产品导向：`Model`、有限元引擎、材料点内部变量、显式/
隐式程序、边界组、接触和断裂能力围绕状态演化组织。AgentFEM Native 应吸收
“模型程序拥有状态生命周期、材料只拥有本构响应”的思想。接触、损伤和断裂
必须等到几何搜索、非线性事务和守恒证据成熟后再进入主线。

AgentFEM Native 自己的差异化不能只是“也能求解”：

1. Windows、macOS、Linux 原生执行同一个契约；
2. 永久保留项目独立维护、基于 NumPy 数组运算的小型有限元数学参考实现；
   这不表示自研 NumPy；
3. 每次计算都有能力、资源、二进制、求解收敛和科学证据身份；
4. Agent 可以先计划、再执行、后解释，并且不能把“运行成功”说成“已验证”；
5. 自研有限元语义与可替换通用计算库并存。
6. 核心串行能力在没有可选国外求解提供者时仍可安装、运行、诊断和验证。

## 三、目标架构

### 1. 求解契约层

Kernel Contract 0.2 已在 2026-09-20 以兼容 0.1 的形式通过 Gate 2 完整验收，
接纳已有科学证据的 T3/T4 线性静力。线性动力继续通过稳定 Python 直接 API
使用，待 Gate 3 证据闭合后再进入后续契约版本，避免接口成熟度领先于科学成熟度。
契约包含：

- 明确的空间维数、分析类型、精度和可重复性策略；
- 网格、命名集合、材料区域、载荷、约束和输出请求；
- 提供者约束和能力协商，而不是泄漏某个提供者的对象；
- 稳定错误码、中文诊断、资源预算和证据要求；
- 模型、计划、二进制、结果和工件的分层摘要。

当前 AF-IR 不进入关键路径。以后 AgentFEM 只需要把工程模型降低到该契约，
Native 不反向依赖 AgentFEM 内部对象。

### 2. `KernelPlan` 执行中间层

新增不可变、可摘要的内部执行计划，统一静力、动力和未来非线性路径。它不保存
工程语言，而保存已经解析的计算事实：

- 拓扑和几何身份、单元批次、DOF 映射和命名集合；
- 基函数/梯度表、积分规则、材料批次和载荷批次；
- CSR/BSR 图、装配策略、约束策略和求解器生命周期；
- 估算内存、线程、临时区、输出和检查点；
- 数学模型不变量与允许的优化实现集合。

这相当于 Agent 请求与 C++ 热循环之间的防火墙。计划发生变化就必须产生新的
摘要，不能在执行途中悄悄改变精度、约束方法或数学模型。

### 3. 单元与积分层

把现有 P1/T3/T4 专用实现逐步收敛为小型、拥有式的 `ElementDescriptor` 和
`Tabulation` 契约：参考单元、值形状、实体 DOF、方向变换、积分精度、几何映射
和输出恢复都显式描述。第一阶段只承载已经实现的 P1 三角形和四面体，不立即
扩成通用单元库。

新增单元的顺序应是：Q4 -> H8 -> P2 三角形/四面体 -> 混合位移-压力。原因是
Q4/H8 对工程网格覆盖最直接，而 P2 与混合空间需要先把实体 DOF、方向变换、
高阶几何和锁死证据做正确。

### 4. 装配与算子层

生产路径从“生成大 COO 再压缩”转向“符号图一次构建、数值多次填充”：

- CSR/BSR 图与数值分离，支持静力重复载荷、动力和非线性迭代复用；
- 按单元类型、材料、积分规则和几何类型分批；
- C++20 使用连续 SoA 数据、预分配输出和有界临时区；
- 提供 `deterministic` 审计模式与 `throughput` 性能模式；
- 先实现 CPU 批处理和线程化，再评估 partial assembly/matrix-free；
- matrix-free 永远不能成为唯一正确性路径，并且必须配可组装预条件矩阵。

线程化优先采用项目自有的静态分块和有界工作队列，避免让核心依赖某一平台的
并行运行时。SIMD 先通过数据布局和编译器向量化获得；Kokkos、RAJA 或其他
可移植层只有在三平台代表性测量胜出后才进入可选实现。

### 5. 稀疏代数与求解器层

保留 Native CSR/BSR、CG、Jacobi/block-Jacobi 作为透明基线，但不自研完整 AMG。
提供者契约需要从单次 `solve` 扩展为：

```text
analyze_pattern -> factor_or_setup -> solve -> update_values -> diagnostics
```

这样静力载荷工况、隐式动力和 Newton 迭代才能复用符号分析与预条件器。Native
下一种自有预条件器优先评估 IC(0)，并以 SPD 失败语义、内存上界和跨平台结果
为准决定是否接纳。对近不可压缩和大规模问题，不承诺用自研基线击败成熟 AMG；
Ginkgo 可作为单节点 CPU/GPU 候选，PETSc/hypre 可作为 Linux MPI/HPC 候选，
都必须通过窄接口、许可证清单、安装能力矩阵和同矩阵基准。

### 6. 程序、状态与材料层

统一静力、显式动力、隐式动力和未来 Newton 的程序生命周期：

```text
begin_step -> predict -> assemble/residual -> solve -> correct
           -> accept/commit | reject/rollback -> checkpoint
```

材料只接收应变/运动学和已提交状态，返回应力、切线、能量和候选状态；材料不能
直接控制全局求解器。所有积分点状态使用明确的布局、版本和迁移规则。Neo-
Hookean 与 J2 先保持材料点 `experimental`，直到方向导数切线、单元响应、路径、
回滚和全局收敛证据全部通过。

### 7. 结果与机器可信证据层

将结果值和证据清单分离：结果可以很大，证据必须小、稳定、可摘要。每次运行
至少记录：请求/计划/二进制身份、平台、精度、提供者、迭代历史、残差、反力、
能量/功平衡、警告、工件摘要和能力成熟度。Agent 的解释只读取这份证据，不
重新运行，也不能修改成熟度。

## 五、接下来四周的执行计划

### 第 0 阶段：两天内完成治理收敛

- 修正项目指令中“Gate 1 是下一里程碑”的过期表述；Gate 0/1 已完成。
- 写出 `KernelPlan`、单元描述、提供者生命周期和可重复性模式的 ADR 草案。
- 冻结 Gate 2/3 的验收矩阵、代表网格和性能测量协议。
- 所有新增重要说明和代码注释执行中文工程表达规范。

### 第 1 周：Gate 2 科学闭环（已完成）

- 已补足 T3/T4 工程算例、网格细化、畸变网格、载荷/约束失败和恢复证据。
- 线性静力已纳入 Kernel Contract 0.2，保留 0.1 兼容，并以请求、计划、执行
  三类摘要绑定证据；源提交 `654fe02` 已通过完整 Tier-1 验收。
- 十万至百万位移自由度的规模基准继续作为 P3 性能任务，不再阻塞已经限定范围
  的 Gate 2 科学成熟度。
- 退出结果：G2-01 至 G2-12 已形成并关闭，能力声明仍明确排除外部验证、非线性、
  MPI、GPU 和生产级成熟度。

### 第 2 周：CPU Production Spine 0.1

- 已完成第一增量：ABI 1.3 T3/T4 确定性 CPU 并行装配、显式线程预算、固定
  归并、Python/Agent 计划集成和代表规模本地记录。该增量不冒充预分配稀疏图。
- 已完成第二增量：`CSRPattern` 参考契约把规范图和多次数值回填分离；ABI 1.4
  已接入按原贡献顺序的 C++20 数值回填并通过三平台验收。当前仍接收元素 COO
  数值数组，不虚构为“已消除中间 COO”。
- 下一增量把可复用图接入真实多载荷/隐式动力装配生命周期，测量端到端收益、
  数据复制和峰值内存，再决定批量回填或直接元素到 CSR 的接口。
- 2026-09-14 本地候选已完成该增量的第一步：T3/T4 预备装配、COO/CSR 双输入
  提供者和 T3 动力刚度图接入。ABI 1.5 候选又让串行预备 T3/T4 只输出数值与
  载荷。下一步收敛到“直接写 CSR—多线程预备归并—预条件器分析/更新—完整
  多载荷求解”链路。
- 实现有界线程池、确定性分块和线程数不变量测试。
- 将 SpMV、残差和 CG 热循环完全移出 Python；测量 GIL 与 Python 开销。
- 评估 IC(0) 与一个成熟可选提供者，不按知名度直接选型。
- 退出条件：代表性 T3/T4 问题上达到 8 核至少 6 倍装配/算子加速的目标，或
  形成诚实的瓶颈报告与替代方案。

### 第 3 周：线性动力学验证

- 增加一维等效杆/二维波传播、临界时间步、时间收敛和色散证据。
- 已完成第一增量：基于稀疏行和的中心差分保守稳定步长预检、受约束 T3 离散
  模态显式/隐式二阶时间细化，以及 Newmark 检查点逐位重启。
- 下一增量完成小型波传播/反射与长时色散，并把隐式有效矩阵接入固定矩阵求解
  计划；时变载荷、阻尼和约束功继续保留明确证据。
- 统一显式/隐式状态事务和能量账本。
- 退出条件：Gate 3 线性部分在同一请求、计划、结果和证据模型下通过本地验收。

### 第 4 周：Agent 力学契约 0.2 候选

- 接纳线性静力与线性动力的版本化 JSON Schema。
- `capabilities -> plan -> execute -> explain` 覆盖 T3/T4、资源预算、取消、重启和
  不支持路径。
- 形成一个 AgentFEM 外部适配示例，但不把 AF-IR 设为依赖。
- 完成本月一次 Tier-1 全平台验收，日常提交仍只使用 Linux 快检。
- 退出条件：Agent 可以安全地判断“能不能算、要花多少、实际算了什么、证据
  到哪一级”，且没有新的公开包发布。

## 六、三到六个月方向

1. **第二个月：** Q4/H8 候选、全局 Newton/线搜索/回退、Neo-Hookean 和 J2
   单元级证据。
2. **第三个月：** P2/混合空间基础、近不可压缩、方向/实体 DOF 变换和高阶几何。
3. **第四个月：** PETSc/hypre 的 Linux MPI 候选、1/2/4/8 rank 一致性与弱扩展；
   串行三平台能力不受影响。
4. **第五个月：** matrix-free/partial assembly 与 GPU 候选，只比较包含数据传输、
   建立和预条件的端到端时间。
5. **第六个月：** Mechanics Alpha 契约冻结、差分模糊测试、恶意输入、长时稳定、
   性能回归阈值、已知限制和内部发布准备。

## 七、明确不做的捷径

- 不照搬 FEniCSx 的 UFL/FFCx/Basix/DOLFINx 实现或内部模型；
- 不让 PETSc、SciPy、Ginkgo、MPI 或 GPU 成为参考层导入依赖；
- 不用更多单元数量掩盖 Gate 2/3 尚未验证；
- 不在没有预条件策略时把 matrix-free 宣传成大规模解决方案；
- 不以单个内核微基准代替端到端求解、内存和守恒证据；
- 不因 Agent 给出自然语言解释而提升科学成熟度。
